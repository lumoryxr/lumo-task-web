# 密码找回模型（方案甲 · 邮箱 + 恢复码）

> 状态：**草案 · 待确认**。对应任务 #16。定稿后再动契约与代码。
> 关联：#14（强制登录 + 多本地用户隔离）、#17（用户名为主注册 + 邮箱后绑定）。

## 1. 已定决策

- **方案甲（访问门）**：本地登录密码只做**用户隔离 + 软锁**，**不加密**任务数据。
  - 依据：桌面端 `lumo.db` 以明文存于 `userData`；`LUMO_ENCRYPTION_KEY` 只加密“存储密钥”（AI key、同步 token），且该密钥与 DB 同目录、非密码派生。
  - 结论：因此不存在“密码+恢复码全丢 → 数据永久锁死”的风险；找回永远可达。
- **恢复方式只保留两种**：**邮箱** 与 **恢复码**。去掉设备级（DPAPI）重置。

## 2. 账号状态 → 找回路径

| 状态 | 首选通道 | 兜底通道 |
|---|---|---|
| 已绑定并验证邮箱（且在线） | 邮件重置链接 | 恢复码 |
| 未绑定邮箱 / 离线 | 恢复码 | —— |

两条通道收敛在**同一个「忘记密码」入口**内呈现；页面按账号能力（有无已验证邮箱、是否在线）决定默认展示哪条、是否两条都给。

## 3. 恢复码（Recovery Code）

- **签发时机**：注册完成即签发并**一次性展示**（见 #17，注册纯用户名，恢复码是无邮箱账号唯一的离线找回锚点）。
- **格式**：`LUMO-XXXX-XXXX-XXXX-XXXX`（Crockford Base32，去易混字符；约 80 bit 熵）。
- **存储**：只存**哈希**（argon2id，与密码同一套哈希策略），明文只在展示当下存在于内存/前端，绝不落库、绝不出现在任何 GET 响应或日志。
- **展示 UX**：注册成功页强制展示 → 提供「复制」「下载为 .txt」→ 勾选「我已妥善保存」后方可继续。
- **生命周期**：
  - 账号页可「重新生成恢复码」→ 旧码立即作废（覆盖哈希）。
  - 用恢复码重置密码后，**建议自动作废该码并提示重新生成**（一次性语义，防止便签泄露长期有效）。
  - 单次消费、限流、失败不区分“码错/码不存在”（防枚举）。

## 4. 忘记密码流程

### 4.1 邮箱通道（已实现，核验为主）
现成页面：`ForgotPasswordPage` → 发送重置邮件；`ResetPasswordPage` → 凭邮件 token 设新密码。
本任务只需**端到端核验**：请求 → dev outbox 取链接 → 设新密码 → 登录；确认 busy 态、错误提示、en/zh 文案齐全。发信依赖 `LUMO_EMAIL_PROVIDER=resend` 等（与找回密码同一套；未配置时 dev 用内存 outbox）。

### 4.2 恢复码通道（新增）
1. 「忘记密码」入口 → 选择「用恢复码找回」。
2. 输入 **用户名 + 恢复码** → 后端校验（限流、恒定时比较、单次）。
3. 通过 → 进入设新密码表单 → 成功后登录，并提示「恢复码已使用，请到账号页重新生成」。

### 4.3 分支决策（前端）
- 有已验证邮箱 → 默认「发送重置邮件」，副入口「用恢复码找回」。
- 无邮箱 → 直接「用恢复码找回」，并提示「绑定邮箱后可用更方便的邮件找回」。

## 5. 契约 / API（契约优先，先落 `@lumo/contracts`）

> 注：auth 域当前用 inline `validate(...)`，尚未迁契约；至少**错误码**走契约，新端点的请求/响应 schema 建议一并纳入契约（与 Task 域参照模式一致）。

| 端点 | 用途 | 备注 |
|---|---|---|
| `POST /v1/auth/recovery-code/verify` | 校验用户名+恢复码，换取一次性 reset ticket | 限流、单次、失败恒定时/不可枚举 |
| `POST /v1/auth/recovery-code/reset` | 凭 ticket 设新密码 | 成功后作废该恢复码 |
| `POST /v1/auth/recovery-code/regenerate` | 账号页重新生成（鉴权） | 返回明文一次，只存哈希 |
| （注册响应扩展） | 注册返回一次性恢复码明文 | 见 #17 |

错误码（新增）：`INVALID_RECOVERY_CODE`、`RECOVERY_CODE_ALREADY_USED`（对外可统一为 `INVALID_RECOVERY_CODE` 防枚举）、`RECOVERY_TICKET_EXPIRED`。

## 6. 后端

- 表 `recovery_codes`：`user_id`、`code_hash`、`created_at`、`used_at`（或直接存 `users.recovery_code_hash` 单条 + 轮换）。建议独立表便于审计与一次性语义。
- 复用密码哈希工具（argon2id）；`crypto.timingSafeEqual` 恒定时比较。
- 复用现有**限流中间件**（auth 敏感端点）与**审计日志**（签发/消费/重生成各记一条，不含明文）。
- 账号删除级联清理 `recovery_codes`。

## 7. 前端

- 注册成功页：恢复码展示组件（复制/下载/勾选确认）。
- 忘记密码页：双通道分支（见 §4.3），busy 态 + 统一错误提示。
- 账号页：「重新生成恢复码」危险操作（二次确认，展示新码一次）。
- api client + store actions；en/zh i18n；CSS token；组件测试。

## 8. 测试（四层）

- **契约**：新 schema/错误码。
- **后端**：恢复码签发/校验/一次性/限流/枚举防护/重生成作废旧码；账号删除级联。
- **前端**：注册展示与「我已保存」门槛、忘记页双分支、账号页重生成。
- **契约一致性 + E2E**：注册→拿码→忘记密码→恢复码重置→登录；及邮箱通道端到端。

## 9. 安全备注

- 恢复码等价于“第二密码”，务必：只存哈希、只展示一次、消费即失效、限流、日志脱敏、错误不可枚举。
- 明确告知用户：本地密码**不加密数据**，同机拥有文件访问权者本就能读到 DB —— 隔离是“软”的；这是方案甲的既定取舍。
