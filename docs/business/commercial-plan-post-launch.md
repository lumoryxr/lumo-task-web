## 0. 一句话结论

工程底子好（84 端点契约化、四层测试、按用户隔离、密钥加密、SSRF 防护）。但**营销开闸前有
三个洞会让投放的钱直接漏掉**，且它们都不是"变现层"：

1. **后端跑在 Render 免费档**，15 分钟无流量休眠 → 投放来的第一批点击大概率打在 30–60 秒
   冷启动上，人还没看到产品就走了。
2. **归因链路只建了一半**——UTM 抓进了 localStorage，但从未上报。你无法回答"哪个渠道
   带来了注册"。
3. **零错误追踪、零转化埋点**——高峰期用户侧报错你看不见，漏斗每一段的流失率你测不出。

先补这三个，再谈收钱。顺序反了的话，你会**烧掉流量、学不到东西，而且照样收不到钱**。

## 2. T-0：营销开闸前必须关闭

投放开始前做完。做不完就**推迟投放**——这些洞会让每一分预算的回报打折且不可归因。

### 2.1 冷启动：后端脱离 Render 免费档 · **S** · 最高优先级

`render.yaml` 声明 `plan: free`。免费档 **15 分钟无请求即休眠**，下次请求要冷启动，实测
量级 30–60 秒。营销的流量天然是脉冲式的——沉寂几小时后一篇帖子带来一波点击，**这波人
100% 打在冷启动上**。

> 若你已在 Render 控制台手动升过档，请核对并同步回 `render.yaml`，别让声明和运行时不一致。

做法（择一）：
- 升到 Render 付费档（Starter 起），休眠即消失。**推荐**。
- 或临时兜底：外部 uptime 监控每 5–10 分钟打一次 `/health` 保温（同时满足 §2.6 的监控需求）。
  这是权宜之计——免费档还有月度小时上限，量上来照样撞墙。

### 2.2 归因闭环：让 attribution 真的上报 · **S**

`attribution.ts` 的注释写得很清楚：

> *"This is deliberately storage-only and contains no network calls. Sending the captured
> value to the backend at signup is an API change, and API shapes are contract-first — so
> that step belongs in its own change."*

也就是说**这件事是被有意留到下一步的，而下一步没做**。当前状态：UTM 抓到了，躺在浏览器里，
注册时不带走，服务端永远不知道人是从哪来的。

做法（契约优先，正是仓库的规范）：
1. `@lumo/contracts` 的 `RegisterBodySchema` / `GithubExchangeBodySchema` 增加可选
   `attribution` 字段（复用已有的 `SAFE_TAG` 约束）。
2. registry 条目 → 后端落库到 `users`（新列 `acq_source` / `acq_medium` / `acq_campaign`）。
3. 前端注册时带上 `getAttribution()`。
4. admin 侧一个按渠道分组的注册数查询。

**这一项是营销的地基**。没有它，后面所有渠道投入都是拍脑袋。

### 2.3 转化埋点：漏斗可测 · **S**

选一个隐私友好的（Plausible / PostHog 自托管，与官网"无第三方广告追踪"的口径一致）。
最少要能测这四段：

```
落地页访问 → 注册完成 → 激活 → 次周回访
```

**先定义"激活"**（否则埋点没有意义）。建议初版：*注册后 24 小时内创建 ≥3 个任务且完成 ≥1 个*。
这个定义可以错，但必须先有，才能优化。

### 2.4 错误追踪：Sentry（或等价物）· **S**

前后端都接。上线后第一波真实用户会打出你测试覆盖不到的路径——没有 Sentry，你只能等用户
主动反馈，而绝大多数人是直接走掉。`docs/ops/reliability-monitoring.md` §1 已有接入方案。

### 2.5 AI 成本闸：确认 `LUMO_AI_CLOUD_GLOBAL_CAP` 已设 · **S**（配置）

代码里的成本防护做得不错：每用户 100 次/月、全局月度上限、原子计数（避免并发绕过）。
但全局闸是 `sync: false` —— **必须在 Render 控制台手动设**，未设即无上限。

营销场景下这是真实敞口：一篇爆款帖 + 未设上限 = 你替所有人付 Claude 的账单。设一个你能
承受的月度数字，并配一条到达 80% 的告警。

### 2.6 确认备份真的在跑 · **S**（核对）

`.github/workflows/db-backup.yml` 是 **opt-in** 的：没配 `TURSO_DATABASE_URL` secret 就
**干净跳过**（notice，不是失败）——所以 **CI 一直是绿的，但可能一次都没备份过**。

去 Actions 看最近一次运行是"跳过"还是"真的产出了 dump"。顺手做一次**恢复演练**——没验证
过的备份等于没有备份。

### 2.7 限流阈值复核（营销场景特有）· **S**

`authRateLimit` 是 10 次/分钟 **按 IP**。正常情况够用，但营销带来的流量有个特点：
大量用户可能**共享出口 IP**（公司 NAT、校园网、部分移动网络、微信内置浏览器）。
一波集中访问下，这些人会互相耗尽对方的配额，表现为"注册不了"。

建议：注册/登录改为**按 IP + 用户名组合**限流，或对已知场景放宽 IP 维度、收紧账号维度。
好消息是上个 PR 已让 429 带上 `Retry-After`，客户端会正确退避。

## 3. T+2~5 周：变现闭环

`commercialization-readiness.md` §2 的方案依然有效，此处只补上线后的差异。**先做完 §2 再开始。**

- **[无] Stripe 接入** · **L** —— Checkout + Billing Portal + webhook（签名校验 + 幂等）。
  契约优先建计费 schema。卡数据不落地，PCI 范围最小化（SAQ-A）。
- **[无] 权益 gate（entitlements）** · **M** —— **服务端**判定，不能只靠前端隐藏。
  好消息：**AI 用量已经是一个现成的计量点**（`ai_cloud_used` / `ai_cloud_month` +
  `plan === "pro"` 分支已在 `routes/ai.ts` 里跑着）。第一个 gate 就用它，改动最小。
- **[无] 升级/降级/取消/宽限期** · **M**
- **[无] 发票 / 税务** · **M** —— Stripe Tax；收据邮件复用现有 `sendEmail()`。
- **[无] 定价页 + 结账入口 + 账号页订阅管理** · **M**

**上线后新增的一条**：既然已有真实用户，**定价决策可以用数据做**，别拍脑袋。
等 §2.3 的埋点跑两周，看 AI 用量分布——免费额度卡在哪个百分位，直接决定 Pro 该卖什么、卖多少。

## 4. T+1~3 月：规模化与信任

- **[无] 限流器换共享存储** · **M** —— 当前是**单进程内存态**。一旦为扛流量加实例，
  有效限额 = 阈值 × 实例数，限流形同虚设。**这是横向扩容的前置条件**，已记在
  `docs/ops/reliability-monitoring.md`。
- **[无] 多实例 / 自动扩容** · **M** —— 依赖上一条。
- **[半] 状态页对外挂出** · **S** —— `/status` 已经有了，挂到独立域名并在支持渠道里公示。
- **[无] 支持 SLA** · **S** —— 收费即义务。先承诺一个你做得到的（如工作日 48 小时）。
- **[无] 合规（收费版）** · 法务 —— 订阅条款、退款政策、税务辖区。见 `readiness` §5。
- **[无] 桌面包签名** · **S–M** —— Windows 未签名会触发 SmartScreen 警告，推广前处理。
- **[无] Postgres 迁移 ADR** · **S** —— SQLite/Turso 单写入是扩展天花板，ADR-0007 已起头。

## 5. 度量体系

没有这一层，上面所有工作都无法判断有没有用。

**北极星指标**：*周活跃且完成 ≥1 个任务的用户数*
—— 比"注册数"诚实（注册可以靠投放刷出来，完成任务不行）。

**必须能回答的六个问题**（对应 §2.2–2.3 的埋点）：

| 问题 | 依赖 |
|------|------|
| 哪个渠道带来注册？ | §2.2 归因上报 |
| 落地页 → 注册转化率？ | §2.3 官网埋点 |
| 注册 → 激活转化率？ | §2.3 + 激活定义 |
| 次周留存？ | §2.3 |
| 免费额度卡住了多少人？ | 已有 `ai_cloud_used`，只需查询 |
| 每个渠道的获客成本？ | 归因 + 投放花费 |

最后一个决定你把钱往哪投。前五个都是它的前置。

## 6. 需要你拍板（阻塞项）

`readiness` §9 的问题**至今没有答案**，其中三个现在开始阻塞工作：

1. **本阶段收费还是继续免费导流？** —— 决定 §3 是现在做还是押后。
2. **Pro 卖什么？** —— 决定权益模型。建议等 §5 的数据（但要先有埋点）。
3. **公司主体 / 经营地？** —— 决定税务与法务辖区，Stripe 开户的前置。
4. **目标市场 CN / 海外？** —— 决定支付渠道（微信支付宝 vs 卡）。Stripe 在国内个人收款受限，
   若主攻国内可能需要 Paddle/LemonSqueezy 这类 MoR，或国内通道。
5. **投放预算与首批渠道？** —— 决定 §2 的紧急程度。

## 7. 建议节奏

```
第 0 周   §2 全部（冷启动 / 归因 / 埋点 / Sentry / 成本闸 / 备份核对 / 限流）
          ↓ 做完才开闸
第 1 周   开始投放，只投 1–2 个渠道，观察漏斗
第 2–3 周 读数据：激活率、留存、AI 额度分布 → 定价决策有依据了
第 3–7 周 §3 变现闭环（与法务并行）
第 2 月+  §4 规模化
```

**唯一的硬性顺序**：§2 在投放之前，投放在定价之前，定价在 §3 之前。
其余可以并行。
