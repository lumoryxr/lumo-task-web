## 0. 一句话结论

部署流水线本身做得比多数项目好：发布是**门禁式**的（push 只构建、手动 dispatch 才碰生产）、
镜像按 SHA 钉住、`.env` 由 GitHub 单一来源渲染、部署后有健康冒烟、有并发锁。

问题不在流水线，在**箱子本身的耐久性**：

> `bootstrap.sh` 负责初始化 VPS，但它**不装备份 cron、不装 logrotate、不装 sqlite3、
> 不配防火墙、不配 swap**。这些全部只以散文形式写在 `vps-deployment.md` 里。
> 也就是说——**保命的那部分工作，靠人记得手动做。**

由此产生的三个高危项，都会在流量上来后才发作：**日志把盘写满**、
**备份很可能一次没跑过**、**没有外部监控**。

## 3. 开闸前必须关闭

### 3.1 Docker 日志无上限 → 磁盘写满 → 全站写失败 · **S** · 最高优先

`docker-compose.prod.yml` **没有 `logging:` 配置**，Docker 默认 `json-file` driver
**无大小上限**。而 app 对**每个请求打一行 JSON 访问日志**（`app.ts` 的 correlation 中间件，
生产环境恒开）。

链路是这样断的：

```
流量上来 → 日志无限增长 → 系统盘写满 → SQLite 无法写入
        → 所有写操作 500 → 而且 Docker 自身也开始故障
```

注意 `LUMO_LOG_FILE` 在部署工作流渲染的 `.env` 里**根本没有这一行**，所以文件 sink 是关的，
所有日志都进 Docker 的 json-file——**唯一的出口恰好是那个无上限的**。
（顺带：compose 里挂的 `lumo-logs:/var/log/lumo` 卷因此是空跑的死配置。）

修复是四行 compose：

```yaml
logging:
  driver: json-file
  options: { max-size: "10m", max-file: "3" }
```

app 和 caddy 两个服务都要加。

### 3.2 备份两条路都没通 · **S** · 数据丢失 = 产品死亡

| 路径 | 为什么没跑 |
|---|---|
| `db-backup.yml`（GH Actions） | 要 `TURSO_DATABASE_URL`。本地 SQLite 模式下没有 → **干净跳过，CI 恒绿** |
| `deploy/vps/backup.sh` | 需要 (a) 手动加 cron、(b) 已装 `sqlite3`。`bootstrap.sh` **两样都不做** |

即使跑起来，默认写到 `$LUMO_DATA_DIR/backups`——**和数据库同一块盘**。盘坏了一起没。
异地副本（`RCLONE_REMOTE`）是 opt-in 的。

**动作**：让 `bootstrap.sh` 承担这件事——装 `sqlite3`、写入 cron 条目、
把异地目标做成显式配置项。然后**做一次恢复演练**。没验证过的备份等于没有备份。

> 先去 Actions 看 `db-backup.yml` 最近一次是"跳过"还是真产出了 dump——
> 这一眼就能确认当前到底有没有备份。

### 3.3 无外部 uptime 监控 · **S**

`/health`、`/ready`、`/status` 三个探针都有，`vps-deployment.md` 里**一次没提监控**。
现在 VPS 挂了，你只能等用户告诉你。营销期间这是不可接受的。

接一个外部监控打 `/ready`（它会真查 DB，且上个 PR 已给它加了 2 秒超时，不会挂死）。

### 3.4 归因闭环 · **S**

`attribution.ts` 的注释自己写明：

> *"This is deliberately storage-only and contains no network calls… that step
> belongs in its own change."*

那个 change 没做。UTM 躺在浏览器里，注册时不带走。**你无法回答"哪个渠道带来了注册"。**

契约优先四步：contracts 加可选 `attribution` 字段 → registry 条目 → 后端落库 → 前端带上。

### 3.5 转化埋点 + 错误追踪 · **S** ×2

漏斗四段（落地 → 注册 → 激活 → 次周回访），外加 Sentry。
**先定义"激活"**：建议初版 *注册后 24h 内建 ≥3 个任务且完成 ≥1 个*。定义可以错，但必须先有。

### 3.6 确认 AI 全局成本闸已设 · **S**（配置）

代码里的防护做得好（每用户配额、全局上限、原子计数防并发绕过）。但全局闸是
GitHub Variable，**未设即无上限**。一篇爆款帖 + 未设 = 你替所有人付账单。

## 4. 应该做、但没到"拦住投放"的程度

### 4.1 无内存上限 → OOM 可能带走整个 box · **S**

compose 没有 `mem_limit`。app 内存暴涨时触发的是**宿主机 OOM killer**，它可能杀掉
Caddy 甚至 Docker，而不只是 app。给 app 设上限后，OOM 只杀它自己，
`restart: unless-stopped` 会把它拉回来——**故障从"全站下线"降级为"一次重启"**。

### 4.2 SSH 用密码认证 · **S** · 安全

部署走 `VPS_PASSWORD`。这意味着箱子的 sshd 开着 `PasswordAuthentication yes`——
暴力破解的常见入口，而 `bootstrap.sh` 不装 fail2ban、不配防火墙。

改用 SSH key（`appleboy/ssh-action` 支持 `key:`），关掉密码登录，
bootstrap 里加 ufw + fail2ban。

### 4.3 指标没人采集 · **S**

`LUMO_METRICS_TOKEN` 会被渲染进 `.env`，`/metrics` 就绪——但**没有 Prometheus 在抓**。
QPS、延迟分布、并发数都在那儿，没人看。营销期间这是"系统现在扛不扛得住"的唯一客观答案。

### 4.4 Caddy 无访问日志 · **S**

`Caddyfile` 没有 `log` 指令。边缘视角缺失——被 Caddy 挡掉的请求、4xx/5xx 分布、
慢请求都看不到。app 层有结构化日志，但那是"进得来的请求"。

### 4.5 单实例 = 发版有停机窗口 · 说明期望即可

`docker compose up -d` 会替换容器：旧的先停、新的再起，中间几秒到几十秒 502。
部署有健康冒烟，但那是**部署后**验证，挡不住窗口本身。

真正消除要蓝绿/多实例（**依赖 §5 的限流器改造**），代价不小。
当前建议：接受它，但**避开流量高峰发版**，并在状态页说明。

### 4.6 限流阈值对 NAT 场景复核 · **S**

注册限流按 IP。共享出口（公司 NAT、校园网、微信内置浏览器）的访客会互相耗尽配额，
表现为"注册不了"。建议改 IP + 用户名组合维度。
（429 已带 `Retry-After`，客户端会正确退避。）
